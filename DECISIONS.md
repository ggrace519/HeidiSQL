# Architecture decisions — HeidiSQL AI Edition

Decisions of the AI Edition fork. Newest last.

## ADR-001: Fork, not an upstream contribution
**Date:** 2026-10-05 · **Status:** accepted

The AI assistant is built in a fork of the upstream `lazarus` branch and is not proposed upstream.
Upstream changes are merged into the fork from time to time.

**Consequences:** fork changes should be easy to merge with upstream. New logic goes into new
units, and edits to existing upstream files are kept to small, clearly marked hooks
("AI Edition: ..." comments). Upstream `.lfm` form files are not edited; new UI is created at
runtime. Fork documentation lives in separate files (`AI-EDITION.md`, `CHANGELOG-AI.md`, this
file) instead of upstream's `README.md` and `CHANGELOG.md`, which is generated by git-cliff.

## ADR-002: Branch model `develop` → `lazarus`
**Date:** 2026-10-05 · **Status:** accepted

`lazarus` plays the role of `main` (released, and where upstream is merged in). `develop` is
the integration branch and the target of every feature PR. Promotion from `develop` to
`lazarus` is a PR merged with a merge commit, never a squash. CI runs on both branches.

## ADR-003: Separate settings folder and display name
**Date:** 2026-10-05 · **Status:** accepted

A stock HeidiSQL and the fork on the same machine would otherwise share
`~/.config/heidisql/settings.json`, `tabs.ini` and tab backups, so each would overwrite the
other's state.

**Decision:** the fork uses the sibling folder `heidisql-ai` (`APPCONFIGDIRNAME`), and shows
"HeidiSQL AI Edition" (`APPDISPLAYNAME`) in captions. `APPNAME` and `GetApplicationName` are
kept, because they also select the translation files and the client name reported to database
servers. On first start the fork offers a one-time copy of the stock settings.

## ADR-004: Own release channel, no upstream statistics
**Date:** 2026-10-05 · **Status:** accepted

The upstream update check would offer stock HeidiSQL releases to fork users, and the upstream
statistics service would count fork installations as stock ones.

**Decision:** the update check reads this fork's GitHub releases and only considers tags
starting with `ai-v`, compared against `AIEDITIONVERSION`. The fork never calls the statistics
service. `ai-v` tags keep fork releases apart from upstream `v12.x` tags mirrored in the fork.

## ADR-005: AI assistant scope and data sharing (v1)
**Date:** 2026-10-05 · **Status:** accepted

- **Providers:** the OpenAI-compatible chat completions API comes first. It covers Ollama,
  LM Studio, vLLM, OpenRouter and OpenAI, so a local model works without data leaving the
  machine. Anthropic comes later.
- **Keys:** API keys are never stored in HeidiSQL settings. They come from an environment
  variable or the OS keychain, because HeidiSQL's password storage is a reversible obfuscation
  and session exports are plain text.
- **Opt-in:** AI is enabled per session and is off by default. Provider profiles are defined
  once in Preferences, and sessions refer to a profile.
- **Shared data:** only schema information (names, types, keys, comments, approximate row
  counts) and the user's own context notes are sent. Sample rows are not sent: they are not
  needed to write SQL, and v2's read-only query tool can fetch real data on demand, with
  approval.
- **No execution:** generated SQL is never executed automatically. It is inserted into the
  editor only on request, and data-changing statements are flagged.

## ADR-006: Layered AI units, context budget and prompt order
**Date:** 2026-10-05 · **Status:** accepted

- **Layering:** wire format, prompts, schema formatting, profiles, conversation and key lookup
  are LCL-free units (`ai.*`) with fpcunit tests. Networking, database access and UI are
  separate units that only pass plain records and strings to them.
- **Context budget:** the default is 8000 characters per request. DDL-like schema text was
  measured at about 2 characters per token on a local model (not the usual 4), so this is about
  4k tokens and fits the default context window of small local models. Profiles can raise it.
- **Prompt order:** rules, dialect, the user's notes and the schema form a stable system
  message, followed by history, with the new question last. Servers with prefix caching reuse
  the processed prefix: a repeated 2.4k-token prompt took 2 s instead of 36 s.
- **Prompt wording is tested against a real model**, not only for structure. Two wordings that
  failed with a 7B model (fix-error echoing the failing SQL, optimize returning it unchanged)
  were replaced by ones that put the instruction after the SQL and name common rewrites.
- **Timeouts:** the default read timeout is 300 s, as an uncached local prompt of 2.4k tokens
  took 36 s before the first token.

## ADR-007: Network worker, cancellation and TLS verification
**Date:** 2026-10-05 · **Status:** accepted

- **Worker and mailbox:** each request runs on its own thread, which only touches an immutable
  request spec and a lock-guarded, reference-counted mailbox. The UI drains the mailbox with a
  timer; nothing is queued to UI objects that could be gone. Cancel finishes the mailbox at once.
- **Cancel:** shuts the socket down at the file descriptor, which wakes a blocked receive,
  including TLS reads. SSL_shutdown is never called from another thread. SIGPIPE is ignored
  process-wide, as OpenSSL's close_notify on a shut-down socket otherwise ended the process.
- **TLS:** FPC 3.2.2's OpenSSL handler verifies neither certificate nor host name. The fork's
  handler does both, with the system's trusted certificates (Windows ROOT store imported) plus an
  optional extra CA file. Untrusted certificates must be allowed explicitly per profile, for
  local servers with self-signed certificates.
- **Redirects are not followed:** the Authorization header would go to another host. The error
  names the redirect target so the user can correct the base URL.

## ADR-008: Assistant panel, request lifecycle and database requirement
**Date:** 2026-10-25 · **Status:** accepted

- **UI in code, not .lfm:** the panel is built at runtime and docked on the right of the main
  window, like the Preferences and Session Manager tabs. main.lfm stays untouched for upstream
  merges. The plan's `ai.panel.lfm` was dropped for this reason.
- **One request in flight** for the whole window, tracked by a request id and the query tab's
  Uid. A 50 ms timer drains the mailbox; text for a cancelled, replaced or closed tab's request is
  dropped. Shutdown cancels and waits up to 2 s for the worker before tabs and settings go away.
- **main.pas coupling** is limited to `ai.hostcontext` (reads the active tab, connection and
  database, puts SQL into an editor) and five short hooks: init before the shortcut snapshot, tab
  change, tree focus change, tab close and shutdown.
- **A selected database is required,** as for Create table: without it no schema is sent and
  the model guesses table names. Picking the only user database automatically was tried and
  rejected, as it hides which schema is sent.
- **Cache-only schema while a query runs:** `TDBConnection` is not thread-safe, so when a query
  thread holds the connection only already cached table lists and columns are used.

## ADR-009: Release process
**Date:** 2026-10-26 · **Status:** accepted; the Assets point about `.deb`/`.rpm` is
superseded by ADR-010, the Tags point (manually pushed tags) by ADR-011

- **Tags:** a release is published only for `ai-v<version>` tags on `lazarus`, after `develop` was
  promoted. The tag must match `AIEDITIONVERSION` in `source/const.inc`; the release job fails
  otherwise. Mirrored upstream tags (`v12.x`) build but publish nothing.
- **Notes** come from the version's section in `CHANGELOG-AI.md`, not from git-cliff, whose
  configuration describes the upstream repository.
- **Assets:** Linux archives (GTK2, Qt5, Qt6, Qt6 ARM64), named `heidisql-ai_<version>_...`.
  No `.deb` or `.rpm` packages: they use the package name `heidisql` and would replace a stock
  installation. No Windows installer yet, as upstream's installer is not attached to releases
  either. No macOS app yet: upstream's bundle job signs and notarizes with upstream's Apple
  certificates and runs only in their repository; an unsigned app would be blocked by
  Gatekeeper. A macOS release needs the fork's own Apple Developer certificate.
- **Normal releases, not prereleases:** the in-app update check ignores prereleases, so a
  prerelease would never be offered.

## ADR-010: Linux packages under their own name
**Date:** 2026-10-28 · **Status:** accepted

- **Decision:** releases also attach a `.deb` and an `.rpm` package named `heidisql-ai`, built from
  the GTK2 binary, with nfpm and `extra/packaging-ai/nfpm.yaml` (`make packages-ai`). The CI
  builds them on every run, so packaging problems show up before a release.
- **Side by side with stock HeidiSQL:** every installed path and name differs from upstream's
  `heidisql` package: `/usr/share/heidisql-ai/`, `/usr/bin/heidisql-ai`, `heidisql-ai.desktop`,
  and the `heidisql-ai.png` icon. No `Conflicts:`. The executable is installed as `heidisql-ai`
  because GTK takes the window class from the program name, so the desktop entry's
  `StartupWMClass=heidisql-ai` matches only this edition. No code change is needed: on Linux the
  program loads translations and `functions-*.ini` from the folder of the executable.
- **GTK2, not Qt6** (upstream packages Qt6): the Qt6 build needs libqt6pas 6.2.x, while Debian 13
  ships `libqt6pas6` 2.2, so a Qt6 package would install and then fail to start. GTK2 is
  available on Debian, Ubuntu and Fedora. The Qt archives stay available.
- **Dependencies:** GTK2 and OpenSSL (HTTPS for the AI assistant) are required. libsecret and the
  database client libraries are recommended only: the program loads them at runtime, by their
  versioned names, only for the database types in use.
- **Version:** `AIEDITIONVERSION` from `source/const.inc`, package release `1`. The tag cannot be
  used, as `ai-0.1.0` is not a valid Debian version.
- **Upstream files are left alone:** `package-skeleton/`, `deb-control.txt` and the
  `deb-package`/`rpm-package` targets stay as upstream has them, to avoid merge conflicts. They
  still build a package named `heidisql` and must not be used for the fork.
- **Install script:** releases also attach `extra/packaging-ai/install.sh`, so
  `releases/latest/download/install.sh` is a stable URL for a one-line install. It is a release
  asset rather than a file on a branch, so it always matches the packages next to it and only
  appears with a release that has packages. It finds the package through the GitHub API and
  installs it with apt or dnf (sudo when not root).
- **Not yet:** no Qt6 or ARM64 packages and no apt/dnf repository; users download the file from
  the release.

## ADR-011: Automated release pull request and tagging
**Date:** 2026-10-28 · **Status:** accepted

- **Decision:** releases need two merges and no typed commands. After a promotion to `lazarus`
  passes CI, `.github/workflows/release-pr.yml` opens or refreshes a release pull request
  (`release/next` → `develop`), made by `extra/release-ai/prepare-release.sh`. It sets the next
  `AIEDITIONVERSION` and turns the `CHANGELOG-AI.md` `[Unreleased]` section into
  `[<version>] - <date>`. Merging it, then the promotion pull request that follows, publishes
  the release: on a push to `lazarus`, the Lazarus workflow checks whether `AIEDITIONVERSION`
  has an `ai-v<version>` tag and, if not, publishes the release, which creates that tag on the
  pushed commit.
- **Next version from the changelog:** a minor bump when `[Unreleased]` has `### Added` or
  `### Changed`, a patch bump otherwise. To override it, edit the release branch right before
  merging: a later promotion refreshes the branch and replaces such edits. Lasting changes to
  the notes go into `[Unreleased]` on `develop`.
- **The pull request targets `develop`, not `lazarus`:** a version commit made on `lazarus`
  only would leave `develop` behind and need a back-merge for every release. `lazarus` keeps
  receiving only promotions and upstream merges. An upstream merge also publishes a pending
  untagged version, like a promotion does.
- **Tagging in the same run, not by pushing a tag:** a tag pushed with the workflow token does
  not start workflows, so a separate tagging step could not trigger the release. The release
  also uses the binaries built for the pushed commit instead of building again.
- **No release PR while a version is pending:** if `AIEDITIONVERSION` is not tagged yet, its
  promotion publishes it, so no new version is prepared. An empty `[Unreleased]` closes an
  open release pull request.
- **What ships is what was promoted:** changes merged into `develop` after the release pull
  request but before the promotion are in that release's binaries while their changelog entries
  go to the next version. The promotion pull request's commit list is the exact content.
- **Refreshing across workflow changes:** the workflow token may not update a branch across
  changes to `.github/workflows`, so the release pull request is closed and opened anew then.
- **No checks on the release pull request:** branches and pull requests made with the workflow
  token start no workflows, so the release pull request shows no checks. It changes only the
  version and the changelog; merging it runs the full CI on `develop`, and the promotion pull
  request is checked before anything is published.
- **Docs-only promotions start nothing:** the Lazarus workflow skips pushes that change only
  documentation, so such a promotion opens no release pull request; run `gh workflow run
  release-pr` by hand if one is wanted. A release pull request always changes
  `source/const.inc`, so its promotion does run CI and publishes.
- **Manual tags no longer publish.** ADR-009's other points stay: notes from `CHANGELOG-AI.md`,
  normal releases rather than prereleases, mirrored upstream tags publish nothing.

## ADR-012: Release integrity: checksums, provenance and a check after publishing
**Date:** 2026-10-28 · **Status:** accepted

- **Checksums:** every release attaches `SHA256SUMS` for all its assets.
- **Build provenance:** the release job signs a SLSA provenance attestation for every asset
  (`actions/attest-build-provenance`, pinned by commit, keyless through GitHub's Sigstore
  instance). `gh attestation verify <file> -R ggrace519/HeidiSQL` proves that a file was built by
  this repository's CI on `lazarus`. No signing key to keep or rotate.
- **The install script checks before installing:** `install.sh` refuses to install a package
  whose SHA-256 does not match `SHA256SUMS`, or a release without `SHA256SUMS`. That catches
  damaged and incomplete downloads; as both files come from the same release, only the
  attestation proves where a file was built.
- **Checked from the outside after publishing:** `.github/workflows/release-verify.yml` runs
  after a `lazarus` run that published a release (or by hand for any tag). It downloads the
  release, checks that every expected asset is there, verifies checksums and attestations, and
  installs it with the release's `install.sh` on Debian 13, Ubuntu 24.04 and Fedora 43, then
  starts the program under Xvfb. If an automatic check fails, the release is marked as a
  prerelease: that hides it from `releases/latest`, so the one-line install and the in-app
  update check go back to the previous release until a fixed version is published. Network steps
  retry three times so a mirror hiccup does not hide a good release; if one does, `gh release edit
  <tag> --prerelease=false` restores it. Runs that failed after publishing are checked too.
- **Older releases:** 0.2.0 and earlier have neither checksums nor attestations; the check reports
  that as a warning instead of failing.
- **Not done:** no GPG signatures on the `.deb`/`.rpm`. Checksums and provenance give the same
  assurance without a key to manage. Signing becomes worth it with an apt or dnf repository,
  where the package managers expect it.
